# M1: Foundations implementation plan

Status: **M1_AWAITING_OWNER_APPROVAL**. Execution mode: **planning_only**.

This is a plan, not implementation evidence. No application code, new Git repository, dependency installation, migration, deployment, or model invocation is authorized by writing this file. The explicit gate is §16 of [the product specification](../../planning/Systems%20Labs%20Product%20Specification.md): propose M1, obtain owner approval, implement and test M1, then stop and report.

## Source and scope

The product specification is authoritative. Its §13 M1–M8 order supersedes the older milestone sequence in `planning/AGENT_HARNESS_PLAN.md`. The master operating rules are in `docs/AGENT_DEVELOPMENT_SYSTEM.md`; `agents/requirements.json`, `agents/backlog.json`, `agents/config.json`, and `agents/task.schema.json` supply traceability, task/run limits, path ownership and handoff contracts.

M1 delivers the monorepo, CI, design system, authentication, database, onboarding, and an empty learner dashboard. A learner can sign up, verify email, set a background, and reach that dashboard. CI runs tests, lint, and type checks. The broader specification also requires password reset, Google/GitHub sign-in, accessible states, translations, authorization, and rate limiting; the shorter milestone acceptance sentence does not waive them.

M1 does not implement the visualizer, lab content/player, mastery, paid catalog, Stripe, coach, sketchpad, or architecture simulation. These belong to M2–M6 in the stated sequence. Existing Python/static prototype files and PDF sources remain reference material and are not automatically copied into the new application's public assets or deployment.

## Routine technical defaults

Record the final pinned versions and rationale in `docs/decisions.md` after approval and before installation:

- pnpm workspaces and TypeScript; Next.js App Router with route handlers under `/api/v1`.
- PostgreSQL with Drizzle schema/migrations; Zod for request and configuration validation.
- Better Auth as the established authentication library, with its supported Drizzle adapter and email/password, verification/reset, Google, and GitHub flows. Confirm library APIs against the selected version before implementing. Do not implement custom cryptography or OAuth protocols.
- Redis for shared rate limits; PostgreSQL remains the durable store. Define the failure policy rather than silently bypassing limits when Redis is unavailable.
- Local captured email for development and CI, plus an environment-configured mail adapter for staging. CI must not send real user email.
- Shared UI primitives and English translation resources, with light/dark themes and locale-ready lookup. Labels, validation/errors, onboarding text, empty/error/loading states, and email templates use translation resources.
- Containerized local PostgreSQL/Redis/mail capture and a containerized staging build. CI uses isolated test data and no production credentials.
- Use GitHub Actions for proposed CI/job coordination and Docker for repeatable execution, following `docs/operations/GITHUB_ACTIONS_DOCKER.md`. This does not imply a working agent model adapter, remote repository or deployment already exists.
- A temporary working name and localhost/staging URLs. Final brand and production domain remain deferred §14 decisions.

The harness is planned, not an already working runner. Until its coordinator exists, the lead follows the same task, worktree, evidence, and review contracts manually; it must not claim an automated execution capability. M1 needs durable managed-session artifacts and controlled dispatch, not implementation of an entire autonomous scheduler/sandbox runtime before the authentication foundations.

## Data model and migration contract

Use the selected Better Auth version's documented table/adapter requirements rather than guessing its exact column names. Logical responsibilities are:

| Entity | M1 information and invariants |
|---|---|
| User / profile | Stable ID, unique normalized email where required by the auth library, verified status, display name, timestamps; background, level, goal, optional interview date, locale, onboarding state. Null/default profile values preserve skippable onboarding. |
| Auth accounts | Library-managed credential/provider linkage. Google and GitHub identities must not accidentally create duplicates or bypass the library's supported account-linking and verification rules. |
| Sessions | Library-managed sessions, expiry and revocation, secure cookie policy. Sessions belong to one user and survive only according to configured expiry rules. |
| Verifications / resets | Library-managed verification/reset tokens with expiry, single-use handling and appropriate storage protection. Do not place token values in analytics or ordinary logs. |
| Audit events | Actor reference, action, target and timestamp for meaningful account/profile changes. Minimize recorded personal data; no passwords, tokens, raw mail, or full request bodies. |

Choose explicit enum/union values for background (`frontend`, `backend`, `mobile`, `data`, `new-to-tech`), level and goal. Validate the optional interview date as a date, not an accidentally shifted timestamp. Store operational timestamps in UTC. Default locale to `en`; support skipped onboarding without manufacturing a skill or readiness score.

Profile/onboarding APIs derive the user from the server session. They never trust a submitted `user_id` as permission. Readiness, lab ownership, attempts and mastery are not represented by fabricated M1 data. Design stable ID/version conventions now and add their real tables in the milestones that implement them.

Migrations must work on an empty database and a database containing a seeded M1 account. Production-like migrations use a separate privileged execution role; normal application access uses a restricted role. Document forward migration, release compatibility, backup and restore behaviour. Backups become operational when M1 starts storing accounts; their existence is not demonstrated by a configuration file alone.

## Verification matrix

Every result must identify the tested commit/build and the environment. Fixture-based tests are repeatable evidence, not a substitute for successful staging provider flows.

| Area | Required checks |
|---|---|
| Workspace / CI | Clean checkout install from lockfile; type/lint/unit/E2E/build commands; no secret or PDF corpus leakage into public artifacts; CI status belongs to the submitted revision. |
| Persistence | Fresh migration and seed; uniqueness constraints; supported provider linkage; expired/revoked sessions; rollback/restore compatibility. |
| Signup / verification | Valid/invalid input, duplicate-account behaviour, captured verification mail, valid/expired/reused token, unverified-account restrictions and resend rate limits. |
| Password / sessions | Correct/incorrect sign-in, sign-out invalidation, reset request and completion, expired/reused reset token, protected route access, safe cookies/CSRF handling. |
| Google / GitHub | Callback state/error handling, successful provider sign-in and approved account-linking policy; local fixtures plus separately identified real staging checks with configured provider credentials. |
| Onboarding | Skip, save and later update; all permitted backgrounds; invalid enum/date rejection; optional fields; no cross-user read/update; ordinary completion under 60 seconds. |
| Dashboard | Authenticated empty state, clear next action/profile route, unauthenticated redirect, loading/error/retry, no invented ownership/completion/mastery. |
| UI / accessibility | Light/dark themes; mobile/tablet/desktop; visible focus; keyboard-only signup/reset/onboarding; labelled errors and screen-reader form states; adequate contrast and reduced-motion behaviour. |
| Localization | No user-facing literal strings outside designated translation resources except documented third-party content; English lookup and missing-key checks; localized email copy and typed-error presentation. |
| Limits / failures | Atomic shared rate limiting, bounded retries, Redis/mail/database failure responses, no silent limit bypass, learner input preserved where appropriate, no credential/token leakage. |
| Operations | Staging build/commit identification, safe health response, structured logs/traces, documented account/onboarding event schema, backup/restore exercise and deployment rollback. |

Production or external provider configuration that is unavailable is recorded as outstanding evidence. Never relabel mocked OAuth, local mail capture, mobile emulation, or a local server as a successful real-provider or physical-phone staging check.
